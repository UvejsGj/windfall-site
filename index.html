Windfall.

An apple the wind has dropped from the tree.

AirDrop for Windows and Linux, rebuilt from the bytes up.

Windfall is a from-scratch implementation of Apple's AirDrop protocol, worked out by capturing and measuring it. Nothing is wrapped and nothing is taken on faith: every layer is tested against software we did not write. Real iPhones have AirDropped photos to it, and they arrived byte for byte.

The one thing to understand first.

AirDrop finds its peers over AWDL, a second Wi-Fi link layer that shares the radio with the normal connection in time slots, on a schedule kept by every Apple device in range. Windows gives an application no way to drive a Wi-Fi card like that, and an iPhone looks for AirDrop nowhere else.

The beacon that starts every transfer shows why there is no way around it. It is 18 bytes long.

0p11p22p33p4 400500600700 803 9a110a211f112f213b114b215e116e2 1700
  • 0 to 3, a prefix. It carries data and is not yet explained.
  • 4 to 7 and 17, zeros. The closing zero has held since iOS 12.
  • 8, a version. Older research found 01. This phone sends 03.
  • 9 to 16, four short values. Two are the first two bytes of a SHA-256 of the owner's phone number and email.

No field names a channel, an address or a transport. The beacon cannot send a peer anywhere else. It can only mean: wake AWDL.

Why it is slow

The speed is the radio, and that is measured. The card under test can only listen in plain monitor mode, so it never acknowledges the frames the phone sends. The phone takes each frame as lost and sends it again until it reaches its retry limit.

sentagainagainagainagainagainagain

Six captures in session 10 agreed. Each frame went out about seven times, so 86% of what the phone sent was a resend. Nine sessions of software changes could not move the rate, because none of them could make this card acknowledge.

Evidence Everything above the radio is written in this repository.

Tested against things we did not write.

A codec can be wrong in a way that round-trips through itself perfectly. So each layer is checked against an independent implementation, and where none exists, against Apple's own devices.

  • LayerWhat is builtChecked against
  • Binary plistBuiltA bplist00 reader and writerChecked againstPython plistlib, which writes our fixtures and reads back what we emit
  • CPIO archiveBuiltA newc writer, and a reader for newc and odcChecked againstbsdtar and libarchive, in both directions
  • DVZipBuiltChunked zlib with stored blocks, and a gzip fallbackChecked againstReal iPhone uploads. No other implementation exists to compare with
  • mDNSBuiltThe DNS wire format and the AirDrop service recordsChecked againstpython-zeroconf, which resolves PTR, SRV, TXT and both address families
  • TLS and HTTPBuiltSelf-signed certificates and a minimal HTTP/1.1 client and serverChecked againstopendrop, as client and as server
  • Discover, Ask, UploadBuiltThe transfer state machine, both halvesChecked againstopendrop both ways, byte-identical, and iPhones for receiving
  • Continuity beaconBuiltA Bluetooth capture tool and a parserChecked againstA real iPhone, not a write-up
  • AWDL linkBuiltNot built here. OWL provides awdl0 on LinuxChecked againstThis is the layer that limits everything above it

    02 · Scan

    The PC shows a code. The iPhone's camera reads it.

    The code holds the PC's address and a secret token: 128 random bits, new every run. Safari opens the page. Any request without the token gets a 404.

    On screenThe PC shows a QR code, the address http://192.168.1.20:52814/ with the token after it, and a New link button. The phone's camera frames the code and offers to open "192.168.1.20" in Safari. A request with the token crosses to the PC, the page comes back, and Safari shows STUDIO-PC: "Send files both ways over this Wi-Fi. No app needed."

  5. 0:27

    03 · Send, in order

    The phone sends the list first, then the files.

    One POST /<token>/upload. The form fields arrive in a fixed order, and the order is the point.

    On screenOn the phone, five photos are chosen, IMG_4101.jpeg to IMG_4105.jpeg, and Send 5 files is tapped. The phone reads "Waiting for STUDIO-PC to accept…". Then the three fields, in order. 1, from: a guess at the device, "iPhone", from the browser, for display only. 2, manifest: a JSON list of {name, size} for every file it is about to send. No list, no question: an upload without one is refused. 3, file × n: the files themselves. The PC reads the first one's headers, then stops and asks.

  6. 0:38

    04 · Ask before reading

    The PC asks before it reads a single byte of a file.

    The list is what the person sees. Until they answer, the upload waits in the socket and TCP holds the phone back, so nobody can push a file onto the PC unasked.

    On screenfrom, manifest and the first file's headers cross to the PC. It asks: "iPhone wants to send 5 files. 3.6 MB together. Nothing is saved unless you accept," and lists the five with their sizes. The rest of the upload is marked held by TCP. The pointer clicks Accept.

  7. 0:46

    04 · Accepted

    Accept, and the bytes flow at Wi-Fi speed.

    Files are staged, then committed all or nothing. Five photos, 3.6 MB together, arrived intact from a real iPhone.

    On screenEach file is ticked off in Downloads\Windfall. The PC reads "Saved 5 files from iPhone", a 200 OK goes back, and the phone reads "Sent 5 files."

  8. 0:54

    05 · The list is binding

    What was agreed to is what lands on disk.

    Each file is saved under the name the list gave it and may be no larger than the list said. Any mismatch fails the whole upload.

    On screenAgreed at the prompt: photo.jpg, 1.2 MB, 1 file. What the page sent: photo.exe, 40 MB, 2 files. A not-equal sign stands between them. Then four rules: name taken from the list; no larger than listed; count must match; a mismatch fails the whole upload, and nothing is kept.

  9. 1:03

    06 · Decline

    Say no, and the phone hears it.

    The refusal goes out while the phone is still uploading. Safari shows "Declined on" the PC's name, and nothing is left behind: no file, no staging folder.

    On screenThe phone sends one file, IMG_4120.jpeg, 1.6 MB, and the PC asks about it. The pointer clicks Decline, a 403 Declined crosses back, and the phone reads "Declined on STUDIO-PC." The PC reads "The phone was told. Nothing was written: no file, no staging folder," and its staging folder, Downloads\Windfall\.incoming-…, is marked removed.

  10. 1:11

    07 · The other way

    The PC can offer files back to the phone.

    Only while the phone sheet is open. Each offer has a generation number, so an old link stops working the moment the offer changes. Downloads land in the Files app.

    On screenThe PC offers holiday-01.jpg, holiday-02.jpg and clip.mp4 as offer #4, while its sheet is open. The phone downloads holiday-01.jpg with GET /files/4/0, and a banner says it was saved to Files. A request for the offer before, GET /files/3/0, gets a 404.

  11. 1:22

    08 · Security model

    Two locks, and plain HTTP on purpose.

    Safari shows a full-page warning for a self-signed certificate. Rather than teach people to click through it, the page relies on the token, the prompt and the Wi-Fi's own encryption.

    On screenLock 1, the token: 128 random bits as the first path segment, compared in constant time. A wrong or missing token gets the same 404 as a page that doesn't exist. Lock 2, the prompt: anyone with the link can ask to send files, but nothing is written until the person at the PC agrees, and New link takes the address back. Protected: from outsiders, by the Wi-Fi's encryption, and from others on the network without the link, by the token. Not protected: from someone on the same network who can intercept traffic. So: home and other trusted networks.

    Tested with a real iPhone on iOS 27.0.1.

    The Windfall app on plain Windows, over home Wi-Fi.

    On screenFour results, each ticked. The camera read the code from the app; Safari opened the page. One photo, then five in one send, arrived intact (Safari converts HEIC to JPEG). A decline reached the phone as "Declined on", leaving nothing behind. Five images and a video downloaded from the PC to the phone. It ends on "Not AirDrop. Just the Wi-Fi you already have." and uvejsgj.github.io/windfall-site, then fades to the colour of the page.

Run it Needs the .NET 8 SDK. The desktop app is Windows only. The command line also runs on Linux.

Build it and send something.

git clone https://github.com/UvejsGj/Windfall.git
cd Windfall
dotnet build

dotnet run --project src/Windfall.App              # the desktop app
dotnet run --project src/Windfall.Cli -- receive
dotnet run --project src/Windfall.Cli -- send photo.jpg
dotnet run --project src/Windfall.Cli -- browse    # list nearby peers

To receive from an iPhone, clone the linux branch and follow the hardware runbook. The receiver asks before it saves anything, and that prompt is the only real security boundary in the protocol.
